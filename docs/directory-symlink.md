# ディレクトリのシンボリックリンク対応

`linkmap.conf` の 1 エントリを、ファイルだけでなく**ディレクトリ**にも
使えるようにした変更の説明です。ファイル向けの既存動作は変えていません。

## 何が足りなかったか

これまでの処理は「LINK も TARGET も 1 個のファイル」と決め打ちしていました。
ディレクトリを linkmap に書くと、次の箇所で失敗します。

| 箇所 | ファイル前提 | ディレクトリだと |
|---|---|---|
| `build-shared-links.sh` の `SHARED_CONF_SYMLINK=off` | `[ -f LINK ]` だけ許可 | 実ディレクトリがあるとビルド失敗 |
| 同 `on` の退避 | `cp -p` (ファイルコピー) | 中身が退避されない |
| 同 `on` の差し替え | `rm -f LINK` | ディレクトリは消えず、`set -e` でビルドが落ちる |
| 同 `on` の権限 | `chmod 0644` | ディレクトリに付けると実行ビットが落ちて辿れなくなる |
| `shared-conf-entrypoint.sh` のシード | `link(2)` で公開 | ディレクトリの hard link は Linux では作れない |
| 同 検証 | `wc -c < LINK` | ディレクトリを読むと失敗し、起動が落ちる |
| `deployment-overlay.sh` | ファイル内容を WAR に被せる | ディレクトリは overlay の content にできない |

## 変更方針

エントリが**実ディレクトリ**のときだけ分岐する。ファイルの経路
(`cp -p` / `chmod 0644` / `link(2)` / `wc -c`) はそのままです。

実ディレクトリの判定は `[ -d path ] && [ ! -L path ]` です。
シンボリックリンク自体は `-d` だとリンク先を見てしまうので、
「ノードそのものがディレクトリか」は `-L` で除外します。
実行時の検証で「リンク先がディレクトリか」を見るときは、逆に
`-L` かつ `-d` (リンクを辿った結果) を使います。

## 変更したファイル

### 1. `image/bin/build-shared-links.sh` (ビルド時)

- `off`: 実ファイルに加えて実ディレクトリも「そのまま維持」で通す。
- `on`: 実ディレクトリは `cp -a` で `defaults/` に退避する
  (配下の相対シンボリックリンクもそのまま残る)。
- 退避先がディレクトリなら `chown -R` のみ。`chmod 0644` はしない。
- 差し替え前の削除は、実ディレクトリだけ `rm -rf`。
  シンボリックリンクやファイルは従来どおり `rm -f`
  (`rm -rf` を symlink に使うと、末尾 `/` が無い限りリンク自体だけ消えるが、
  ここでは実ディレクトリに限定している)。
- `LINK` が `/` または末尾 `/` のときは `rm -rf` しない。

### 2. `image/bin/shared-conf-entrypoint.sh` (実行時)

- 実体が既にあるディレクトリなら、中身を比較せず維持する
  (`cmp` はディレクトリを比較できない)。
- まだ無いときは、シード元ディレクトリを
  `cp -a --no-preserve=ownership` で一時ディレクトリにコピーし、
  **同じ親ディレクトリ内の `mv -T`** で公開する。
  - ファイルの `link(2)` と同じく、先に作った側があると失敗する。
  - 失敗した側は自分の一時ディレクトリだけ消し、先勝ちの実体は触らない。
  - コピーが終わってから名前を出すので、他コンテナから中途半端なツリーは見えない。
- `mv -T` は GNU coreutils のオプションです。対象の RHEL 9.8 には標準で入っています。
  一時名と公開名が同じディレクトリ上なので、EFS (NFSv4) でも rename はアトミックです。
- 検証ログはディレクトリのとき `wc -c` を使わず `(directory)` と出す。
  辿るには読み取りに加えて実行ビットが要るので `-x` も見る。
- `off` の検証も実ディレクトリを許可する。

### 3. `image/bin/deployment-overlay.sh`

Deployment Overlay は「アーカイブ内の 1 ファイル = ローカルの 1 ファイル」です。
ディレクトリエントリはここでスキップし、同じ linkmap にあるファイルエントリだけ
従来どおり overlay します。

ディレクトリだけの linkmap で `SHARED_CONF_OVERLAY=on` の場合は、
対象ファイルが 0 件である旨を出して overlay は成功終了します
(ファイルが 1 件も無い linkmap の失敗とは区別しています)。

### 4. `ec2/init-shared-conf.sh`

`--seed` にディレクトリを渡せるようにしました。
basename で `${SHARED_CONF_DIR}` 配下へ `cp -a` し、`chown -R` します。
既存があればファイルと同じく上書きしません。

`edit-shared-conf.sh` は properties ファイル用のままです。
共有ディレクトリの中のファイルを編集するときは、そのファイルパスを渡してください。

### 5. `image/linkmap.conf`

書式は変えていません。ディレクトリの記入例をコメントで 1 行足しただけです。

## 使い方

`linkmap.conf` にディレクトリの絶対パスを 1 行書く。第 4 列 (overlay の
アーカイブ内パス) は使わないので `-` のままにします。

```
${APP_ROOT}/servlets/jp/co/sample/base/conf   ${SHARED_CONF_DIR}/conf   -   -
```

ビルドと実行のフラグはファイルのときと同じです。

```
docker build --build-arg SHARED_CONF_SYMLINK=on ...
```

実行時、EFS 上に `/mnt/logs/tmp/conf` が無ければイメージ内の初期ツリーから作られ、
あれば中身は一切上書きされません。front / back の symlink は同じディレクトリを指します。

イメージに初期ツリーが無いビルドにする場合は、先に EC2 で実体を置きます。

```
sudo ./ec2/init-shared-conf.sh --seed /path/to/conf
```

## やってはいけないこと

- **ディレクトリと、その中のファイルを両方 linkmap に書かない。**
  先にディレクトリを symlink に差し替えると、配下のファイルエントリは消えたり、
  リンクの中へ書きにいったりします。ディレクトリごと共有するか、
  必要なファイルだけを個別に共有するか、どちらか一方にしてください。
- 共有ディレクトリに `chmod 0644` 相当を期待しない。
  ファイルエントリだけが `SHARED_CONF_MODE` (既定 `0664`) を明示適用します。
  ディレクトリのモードはイメージ側のモードを `cp -a` で引き継ぎます。
- overlay でディレクトリツリーを WAR に展開することはできません。
  WAR 側はこれまでどおりファイルエントリだけが対象です。

## 確認

```
bash test/selftest.sh          # ファイル共有 (既存)
bash test/selftest-nolink.sh   # symlink=off (既存)
bash test/selftest-overlay.sh  # overlay (既存)
bash test/selftest-dir.sh      # 今回のディレクトリ共有
```
